# Postman

- `DisputePortal.postman_collection.json`: every API endpoint, with test scripts.
- `DisputePortal.local.postman_environment.json`: variables for the local Docker setup.

## Use it

1. Start the API: `docker compose up --build -d` from the repo root. It listens on http://localhost:8080.
2. In Postman, **Import** both files and select the **Dispute Portal - Local** environment.
3. Run the requests top to bottom, or run the whole collection with the Collection Runner.

The scripts pass values along, so no ids need copying:

| Request | Saves |
|---|---|
| Auth / Customer login | `customerSession` |
| Auth / Other customer login | `otherCustomerSession` |
| Customer / List transactions | `transactionId`, `transactionAmount` (first disputable transaction) |
| Customer / Raise dispute | `idempotencyKey` (before sending), `disputeId` |

Requests send `customerSession` as a `Cookie: dp_session=...` header unless they say otherwise. The collection turns off Postman's cookie jar so the two customers' sessions never mix.

## Variables

| Variable | Default | Notes |
|---|---|---|
| `baseUrl` | `http://localhost:8080` | |
| `customerEmail` | `thandi@example.com` | Seeded customer |
| `otherCustomerEmail` | `sipho@example.com` | Second customer, for the cross-customer 404 check |
| `password` | `Demo@12345!` | Shared by every seeded account, Development only |
| `customerSession`, `otherCustomerSession` | empty | Session ids, set by the login requests |
| `transactionId`, `transactionAmount` | empty | Set by List transactions |
| `disputeId` | empty | Set by Raise dispute |
| `idempotencyKey` | empty | Regenerated by each Raise dispute |

## Ids go in the body, not the URL

Single-item calls are POSTs with the id in a JSON body, so ids never appear in URLs, access logs, proxy logs or browser history:

| Call | Body |
|---|---|
| `POST /api/transactions/lookup` | `{ "transactionId": "..." }` |
| `POST /api/disputes/lookup` | `{ "disputeId": "..." }` |
| `POST /api/disputes/withdraw` | `{ "disputeId": "...", "note": "optional" }` |

A missing id is 400. Another customer's id is 404, the same as an id that does not exist.

## Validation fails fast

Bad input is a 400 before any database work. The **Validation (fail fast)** folder, and **Withdraw with a too-short note is 400** in Customer, check that:

- each field in `errors` has exactly one message, for the first rule it broke, under the JSON name the client sent (`note`, not `Note`);
- free text (description, withdraw note, search, login email) rejects control characters and invisible bidi overrides such as U+202E; the description and note allow line breaks;
- a withdraw note is optional, but 5-500 characters when given;
- a login email is at most 254 characters.

Messages never repeat the rejected value.

## Notes

- A run raises a real dispute in the local database and then withdraws it, which frees the transaction again, so the collection can be run repeatedly.
- `/api/auth/login` allows 10 requests per minute per client. Running the collection several times in a minute can hit this and return 429; wait a minute.
- A session ends after 5 minutes without a request (every request restarts the timer), 8 hours after sign-in, or at Sign out. On a 401, run the login requests again.
- Reviewing disputes (Under review, Resolved, Rejected) happens in the bank's back office and is out of scope for this API. The seeded disputes already show every status on the portal's timelines.
